# View Component Rules

- Статус: draft
- Тип: обязательные правила разработки
- Назначение: правила проектирования React-компонентов в `view`-слое.

Этот документ описывает способ ведения разработки. Правила нужно применять при
создании, изменении и переносе React-компонентов.

## Основная Модель

VC-01. Компонент является изолированной единицей.

Компонент решает одну мини-задачу. У компонента должна быть понятная
ответственность, граница и причина существования.

Нельзя создавать компонент как:

- случайный кусок JSX;
- техническую группу тегов;
- временное место для разрастания родителя;
- набор unrelated элементов без общего назначения.

VC-02. Каталог компонента является его публичной границей.

Каталог компонента воспринимается как класс в ООП. Внешний код работает только
с публичным входом каталога, а внутренние файлы остаются деталями реализации.

Базовая форма:

```text
component/
├── index.ts
├── component.tsx
└── default.module.css
```

Если в локальном коде принят другой extension style module, он может отличаться.
Правило остается тем же: style file лежит внутри каталога компонента.

Базовая форма не запрещает private файлы реализации внутри каталога компонента:
`*.hook.ts`, `*.helper.ts`. Такие файлы остаются внутренними деталями и не
экспортируются наружу через `index.ts`, если не стали частью public contract.

Отдельные `*.type.ts` и `*.constant.ts` на уровне одного компонента обычно
говорят о неверном масштабе: type или constant должны остаться рядом с
использованием, перейти в более подходящий слой или привести к пересмотру
границы компонента.

VC-03. Внешний код не импортирует файл компонента напрямую.

Запрещено:

```ts
import { Component } from './component/component.tsx';
```

Разрешено:

```ts
import { Component } from './component';
```

`index.ts` является публичным входом и экспортирует только то, что разрешено
использовать снаружи.

VC-04. Внутренние файлы компонента не являются public API.

К внутренним файлам относятся:

- файл реализации компонента;
- style module;
- локальные helpers;
- локальные types;
- вложенные компоненты, если они не экспортированы через публичный вход.

Если внешний код начинает импортировать внутренний файл, значит нарушена граница
компонента или неверно выбран уровень владения.

## Назначение И Имя

VC-05. Имя компонента идет от его назначения.

Имя должно отвечать на вопрос: какую мини-задачу решает компонент?

Имя не должно выбираться только по:

- HTML-тегу;
- UI-kit компоненту;
- визуальному control;
- случайному месту в файле;
- желанию сократить длинный родительский компонент.

VC-06. Имя должно отражать границу владения.

По имени и пути должно быть понятно:

- где компонент используется;
- какую часть композиции он закрывает;
- кто его родитель;
- является ли он самостоятельной единицей или частью родителя.

Если это невозможно понять без чтения реализации, имя или место выбраны плохо.

VC-07. Техническое имя допустимо только когда техническая роль и есть назначение.

Имя по типу control нельзя использовать, если реальная задача компонента шире
или конкретнее. Компонент выбора сущности не должен называться по имени
базового control. Компонент списка не должен называться по имени визуального
control, если его ответственность шире, чем вызов этого control.

## Композиция

VC-08. Компоненты вкладываются друг в друга только через композицию.

Вложенный компонент допустим, если он:

- является частью родительского компонента;
- нужен только для реализации родительской мини-задачи;
- не имеет самостоятельного внешнего сценария;
- помогает родителю не смешивать orchestration и детали отображения.

VC-09. Вложенный компонент живет внутри каталога родителя.

Если компонент нельзя осмысленно использовать без родителя, он должен находиться
внутри каталога родителя.

Форма композиции:

```text
parent/
├── index.ts
├── parent.tsx
├── default.module.css
└── child/
    ├── index.ts
    ├── child.tsx
    └── default.module.css
```

VC-10. Плоский список файлов запрещен.

Запрещено складывать компоненты рядом без выраженной композиции:

```text
view/
├── parent.tsx
├── child.tsx
├── item.tsx
├── action.tsx
└── value.tsx
```

Такая структура скрывает ownership и провоцирует прямые импорты внутренних
деталей.

VC-11. Родитель отвечает за композицию, ребенок отвечает за свою мини-задачу.

Родитель должен определять, какие дочерние компоненты участвуют в сборке.
Дочерний компонент не должен знать лишнего о соседях и не должен управлять
границами родителя.

## Вынос Компонента

VC-12. Компонент нужно выносить, когда появилась отдельная мини-задача.

Вынос обязателен, если часть JSX:

- имеет самостоятельную ответственность;
- имеет собственную разметку и стили;
- повторяется как item коллекции;
- имеет собственное действие;
- использует отдельный локальный контекст;
- усложняет родителя деталями отображения.

VC-13. Компонент нельзя выносить только ради размера файла.

Вынос считается неверным, если после него:

- появляется искусственный props API;
- теряется понятный владелец;
- компонент выглядит общим, но зависит от приватного контекста;
- внешний код начинает использовать его как самостоятельный public API без
  осознанного контракта.

VC-14. Общий компонент появляется только после определения public contract.

Похожая разметка не является причиной делать общий компонент. Перед выносом в
общий слой нужно определить:

- кто владеет компонентом;
- какие props являются стабильным API;
- какие зависимости допустимы;
- не проще ли оставить локальные компоненты.

## Imports И Exports

VC-15. Импорт всегда идет через ближайший публичный вход.

Импорт из внутреннего файла допустим только внутри каталога самого компонента.
За пределами каталога нужно импортировать через `index.ts`.

VC-16. `index.ts` не должен быть свалкой экспортов.

Экспортируй только то, что является public API каталога. Вложенные детали не
нужно экспортировать наружу только потому, что это удобно для импорта.

VC-17. Если понадобился импорт внутренней детали снаружи, сначала пересмотри
границу компонента.

Возможные решения:

- поднять компонент на уровень выше;
- оставить использование внутри родителя;
- выделить новый public component;
- изменить композицию так, чтобы внешний код не знал внутренности.

## Стили

VC-18. Style file принадлежит компоненту.

Стили компонента должны лежать в каталоге компонента. Нельзя складывать стили
нескольких независимых компонентов в один общий style file без отдельной
архитектурной причины.

VC-19. Переименование style files не делается побочным эффектом.

Если задача не про изменение структуры компонента или style convention, не
переименовывай style files только ради единообразия.

## Проверка Решения

VC-20. Перед завершением задай вопрос: можно ли по пути понять владельца?

Если путь не показывает, кто владеет компонентом и какую мини-задачу он решает,
структура требует правки.

VC-21. Перед завершением проверь, нет ли прямых импортов внутренних файлов.

Нарушением считается импорт вида:

```ts
import { Component } from './component/component.tsx';
```

За пределами каталога компонента должен использоваться public entry.

VC-22. Перед завершением проверь, что вложенность выражает композицию.

Если дочерний компонент не является частью родителя, он не должен лежать внутри
родительского каталога. Если является частью родителя, он не должен лежать
рядом с родителем как независимый файл.
