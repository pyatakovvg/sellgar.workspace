# Архивирование каталога и связанных продаж

Статус: реализация согласована пользователем 2026-11-22 («если все понятно, можно приступать»).

## Контракт задачи

- Ветка: development. Владельцы: Product, Store, Cart; непосредственные адаптеры — Admin gateway и Admin UI.
- Перед архивированием Product/Variant запрашивается использование в Store. Подтверждение обязательно даже без связей; при наличии связей предупреждение сообщает о прекращении связанных продаж.
- Product меняет собственный статус, сохраняя UUID, свойства, изображения и личные статусы вариантов. Store архивирует связанные продажи: весь StoreProduct с его предложениями при архиве Product, только соответствующие StoreOffer при архиве Variant. Учётки, цены, остатки и история сохраняются.
- Product.updated и полные снимки остаются источником для Store/Cart. Применение архива и исходящее событие Store атомарны; повторы и старые события не повторяют эффекты.
- Cart сохраняет недоступную строку с «Товар больше не продаётся», исключает из суммы/оформления. Новое добавление и увеличение проверяют владельцев даже при задержке событий; обнаруженный архив обновляет проекцию до отказа, независимо от отката команды.
- Оформление повторно проверяет актуальность. Отказ источника не означает доступность.
- UI не фильтрует архивные коллекции. После изменений перечитывает обычные API владельцев.
- Вне задачи: восстановление, уведомления покупателю, новые сервисы/движки процессов, изменение остатков/истории.

## Приёмка

- Подтверждение/отмена, с использованием и без использования.
- Архив Product во всех магазинах; архив Variant не затрагивает остальные варианты.
- Повтор/переставленные события; полные снимки восстанавливают каскад после сбоя.
- Устаревшая страница: добавление/увеличение/оформление отклонены; сохранённая строка недоступна до доставки события.
- Сумма не включает недоступные позиции, строка доступна для удаления.
- Проверки бизнес-логики, PostgreSQL в изолированных схемах и изолированный runtime smoke. Живые товары не архивируются для проверки.

## Реализация

Product передаёт полный снимок в `store.catalog.synchronizeSnapshot` и ожидает результат.
Если подтверждение потерялось, повтор архивирования уже архивированной сущности доставляет
снимок повторно без новой версии Product. Outbox остаётся путём повторной доставки.
Store применяет каскад в одной транзакции с проекцией и своим outbox.
Cart перечитывает владельцев через существующий recovery перед изменением и оформлением;
обнаруженная недоступность сохраняется даже при отказе команды. Витрина после 409
перечитывает корзину, чтобы показать сообщение без ожидания сокета.

Подтверждены SQL-проверками и smoke через настоящий RabbitMQ: каскад по двум магазинам,
сохранение цен и остатков, повторы и задержанные события, отказ корзины до события Product.
Проверка проводилась на временном брокере и изолированных схемах, без изменения dev-товаров.
Проверка актуальной dev-раскатки выполняется отдельно после публикации.
