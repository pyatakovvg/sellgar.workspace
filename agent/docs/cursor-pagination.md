# Курсорная пагинация списков

Статус: реализация проверена локально, опубликована в development и развёрнута на dev; все девять CI завершились успешно.
Уточнение пользователя: все списочные контракты должны иметь единую форму.

## Задача и границы

По запросу пользователя все действующие сервисы с самостоятельными списочными API
получают limit/nextToken для последовательной подгрузки. Пользователь согласовал
общую библиотеку sellgar.pagination.library по образцу nested outbox submodules.
Библиотека владеет протоколом токена и SQL keyset-выборкой; сервисы — фильтрами,
сортировкой, доступом и составом объектов. Gateway только адаптируют контракт.

| Владелец | Коллекции | Потребители |
| --- | --- | --- |
| Product | товары, типы, свойства, бренды, единицы | Admin gateway/UI |
| Store | продаваемые товары, предложения, валюты | Admin/Client gateway, Cart recovery, UI |
| Shop | магазины | Admin gateway/UI, Cart recovery |
| Cart | административный список корзин | Admin gateway/UI |
| File | файлы, дочерние папки | Admin gateway/UI, собственный HTTP |

Identity и Media не имеют самостоятельных списочных API. Socket replay уже имеет
отдельный курсор доставки событий и не является списком бизнес-сущностей.
Полные снимки агрегатов, вложенные коллекции и дерево категорий остаются полными.
Исторический Product code/_service и неразвёрнутые приложения не изменяются.

## Контракт

- Первый запрос: limit и фильтры; последующие — те же фильтры и nextToken.
- Единый запрос: `{ limit?: number, nextToken?: string, ...filters }`.
  Default limit=50, maximum=100. Единый ответ:
  `{ items: T[], meta: { limit: number, nextToken: string | null } }`.
  Одиночная сущность возвращается напрямую, без items/data/meta.
  Окончательное уточнение пользователя: totalRows полностью исключается.
  COUNT общего количества не выполняется в списочных запросах. Существующие
  предметные атрибуты (itemsCount корзины, число товаров конкретного типа) этим
  не удаляются. Отдельные подсчёты всей выборки через
  views/read models — будущая задача, без заготовок в текущем контракте.
- Последняя страница имеет nextToken=null. Для определения продолжения БД читает
  limit+1 ключей, а не загружает полный список для последующей обрезки.
- Токен связан с endpoint, сортировкой и нормализованными фильтрами; изменение
  условий или повреждённый токен отклоняются как 400. Изменять limit допустимо.
- Токен подписывается HMAC-SHA256. Ключ минимум 32 байта приходит из Secret,
  совпадает у реплик сервиса, не имеет fallback и не публикуется с конфигурацией.
  Подпись проверяется до разбора ключей; HMAC не является шифрованием или доступом.
- SQL использует лексикографическое сравнение ключей и уникальный tie-breaker.
  Даты/ранги читаются как точные SQL-строки, без преобразования через JS Date.
- Пагинируются корни агрегатов до загрузки relations, а не строки JOIN.
- Токен не предоставляет доступ: auth/shop/owner-предикаты применяются всегда.
- Прежние total и limit/offset заменяются единым контрактом, включая
  gateway и непосредственных потребителей. Параллельный legacy paging не сохраняется.
  Неизвестный offset отклоняется в списочном запросе, а не молча игнорируется.
- Бесконечная лента не является снимком БД: изменение полей сортировки между
  запросами может переместить объект. Сортировки выбираются по устойчивым полям.
- Последний ключ сортировки — уникальный PK; его отсутствие является ошибкой
  конфигурации владельца. Набор сортировок задаётся только сервером.
- Индексы создают сервисы своими миграциями. Состав и направления сверяются с
  фильтрами и EXPLAIN (ANALYZE, BUFFERS), включая глубокий курсор. Постоянное
  время не обещается, особенно для вычисляемого полнотекстового rank.

### Проверка SQL-плана общей механики

На 50 000 синтетических корней при границе после 40 000-й записи запрос через
OR использовал индекс, но отбрасывал 40 001 предыдущую строку (4,54 ms).
Непересекающиеся ветви UNION ALL с собственными limit+1 устранили этот проход:
индексные диапазоны, 0 отфильтрованных предыдущих строк, 0,089 ms.
При полностью одинаковых timestamps — 0,096 ms и также 0 отброшенных строк.
Замер выполнен в отдельной временной схеме; это проверка формы базового запроса,
а не SLA всех сервисных JOIN/FTS-фильтров. Их планы проверяются у владельцев.

## Приёмка

- Пустая/последняя/точно заполненная страница, разные размеры пачек.
- Одинаковые даты/ранги, удаление граничной записи, вставка перед курсором.
- В SQL списков нет COUNT, в ответах нет totalRows.
- Отсутствие дублей из JOIN, сохранение полноты вложенных records/options.
- Неизвестный/повреждённый токен, другой endpoint и изменённые фильтры.
- Обход всех Shop/Store страниц при восстановлении Cart.
- DTO и метаданные проходят оба gateway; существующие consumers не обрезают
  выдачу молча. Проверки — unit, PostgreSQL в изолированной схеме и HTTP smoke.
- Раскатка требует согласованного обновления производителей/потребителей;
  до неё новая форма остаётся локальной разработкой и проверяется изолированно.

Основа: [Google AIP-158](https://google.aip.dev/158),
[GitLab keyset pagination](https://docs.gitlab.com/api/rest/#keyset-based-pagination),
[PostgreSQL LIMIT/OFFSET](https://www.postgresql.org/docs/current/queries-limit.html).

## Структура Entity

Каждая Entity и результат списка находятся в отдельных файлах. Вложенные
Entity (изображение бренда, опция свойства, строка корзины) также имеют собственные
файлы и прямые импорты; результат списка не объявляется в файле самой сущности.
Проверены 72 изменённых Entity-файла — смешанных объявлений нет.

## Догрузка таблиц админки

- Scope: восемь route-списков — товары, магазины, склад, корзины, бренды,
  свойства, единицы и шаблоны; текущие ветки development. Сервисы, gateway,
  витрина, дерево категорий и полные справочники форм не меняются.
- Контракт: lastRowTrigger → общий useRevalidate() → Collector → nextToken.
  Таблица использует штатный loading; null завершает список, ошибка сохраняет
  прежнюю порцию и курсор. Изменение фильтра начинает новую выборку.
- Один useRevalidate() без токена контроллера запускает лоадеры модуля;
  его общий inProcess используется для loading и блокировки lastRowTrigger.
  Он учитывает и query-поиск, и догрузку; отдельный targeted hook не нужен.
- Сохраняются EntityCollection и текущие вставки/обновления справочников.
  Проверки: TypeScript host, business tests накопления/завершения/ошибки/смены
  фильтра; локальный API и ручной scroll в браузере. UI-тесты не добавляются.
- Collector сохраняет полученные page Entity. Контроллер возвращает накопленный
  ResultEntity с meta последней страницы, объединяя записи по uuid/code.
  Это сохраняет insertEntity, в том числе вставку между порциями; одна сущность
  не дублируется из-за появления в нескольких реактивных страницах.
- Все 342 business tests админки и TypeScript host проходят. Форматирование
  целевых файлов проверено. ESLint не проверяет TSX из-за действующей конфигурации
  (no matching configuration); это не считается успешной lint-проверкой.
- Все восемь реальных локальных RMQ-источников прочитаны с limit=2 до null,
  без дублей: products 13, shops 5, store 10, carts 19, brands 27,
  properties 15, units 9, templates 14.
- В таблицах размер порции 50; текущие локальные списки меньше одной порции.
  Визуальный scroll-trigger остаётся для ручной проверки на большей выборке;
  автоматический browser-доступ ранее отклонён политикой инструмента.
  После изменения DI bindings и конструкторов нужна полная перезагрузка админки.
