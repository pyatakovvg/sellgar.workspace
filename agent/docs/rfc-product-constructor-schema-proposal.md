# Предполагаемая БД сервиса управления товарами

- Дата: 2026-10-04.
- Статус: **предложение для обсуждения, не принятые дополнения к RFC**.
- Основание: [принятый RFC](rfc-product-constructor.md), включая последнее
  подтверждение каскада «поле типа → назначения наследникам → значения».
- Участники: root, catalog_operator, schema_fit, warehouse_operator.
- Область: только сервис управления товарами и его БД. Сервис склада и учета
  разрабатывается отдельно и в этот проект не входит. Production-код, миграции,
  существующие БД и ранее принятый RFC этой работой не изменены.

**Последующее согласование 2026-10-04:** пользователь подтвердил пункты 1–3
и 5–8 итогового консилиума, отложив пункт 4. Актуальные решения записаны
в [RFC](rfc-product-constructor.md). Ниже сохранен проект и результаты опыта
до этого согласования; его формулировки об открытых вопросах не заменяют RFC.
В частности, `multiple` теперь относится к полю типа, а не Property; приняты
шесть типов значений, технический UUID типа, ручные бизнес-коды, состояния
`active / archived`, редактирование архива, атомарное создание и конфликт
актуальности. Физическая организация списков остается открытой.

SQL-эксперимент еще не приведен к новым правилам поля типа, обязательности
и контрактам сохранения. Его 34 проверки подтверждают только описанный опыт,
а не реализацию всех последующих решений. Обновление SQL выполняется отдельно.

## 1. Вывод

Основная гипотеза работоспособна: общее определение свойства, включение свойства
в тип, назначение поля конкретному наследнику и значения назначения — разные
записи с разным временем жизни. Их можно связать реальными внешними ключами.
Удаление поля типа каскадно удаляет назначения и значения именно его наследников.
Общее свойство, использование в другом типе, товары и варианты сохраняются.

Это проверено исполнением SQL, а не только чтением диаграммы. В PostgreSQL 16.15
прошло 34 проверки в границах сервиса товаров, включая архивирование.
Физическое удаление Product/Variant запрещено по последнему уточнению.
Открыты защита единицы измерения и полный жизненный цикл архивирования.
Модель связей и эти дополнительные гарантии
следует оценивать отдельно.

## 2. Что принято, а что выбрано только для опыта

| Принято пользователем | Техническая гипотеза этого проекта |
|---|---|
| Общее свойство без значения, с фиксированной единицей | `property(code, name, kind, unit_code, multiple)`; место настройки `multiple` еще обсуждается |
| Значения отдельно, один ко многим даже для одиночного значения | Отдельные таблицы назначений и значений для товара и варианта |
| Коды вместо отдельных ID у примитивов | Составные ключи служебных связей; коды строк значений в тесте заданы вручную |
| Типу не нужен бизнес-код | UUID как технический ключ типа только в SQL-опыте |
| Код опции участвует в поиске | Уникальность опции внутри свойства: PK `(property_code, code)` |
| Тип задает структуру товара и общий подтип варианта | Две таблицы полей с одним `type_id`; отдельная сущность подтипа не требуется |
| Товар наследует текущую структуру типа | Незаполненные назначения создаются при вводе значений; перечень полей читается из типа |
| Поле типа удаляет назначения и значения каскадно | Два последовательных `ON DELETE CASCADE`, составные FK для принадлежности |
| Первый вариант присутствует сразу, товар не бывает без вариантов | Отложенная проверка наличия записи Variant при создании; минимум неархивированных вариантов не определен |
| Product и Variant никогда не удаляются, только архивируются | `archived_at` как экспериментальная отметка; запрет DELETE/TRUNCATE в опыте |

Шесть типов в SQL (`text`, `integer`, `decimal`, `boolean`, `date`, `options`),
`numeric` для дробного значения, формат HEX из шести цифр, область уникальности
кодов и правила удаления используемых справочников — параметры опыта, а не
автоматически утвержденные продуктовые решения. Служебный `code` строки значения
не означает, что оператор должен придумывать его вручную.

## 3. Каталог: таблицы и направления связей

```text
unit ← property → property_option → option_extra → image
          ↑
          ├─ type_product_property ← product_property → product_property_value
          │          ↑                    ↑
          │     product_type ←──────── product ← brand
          │          ↑                    ↑
          └─ type_variant_property ← variant_property → variant_property_value
                                          ↑
                                        variant → variant_image → image
                                          │
                                          └─ принадлежит product
```

Диаграмма показывает роли сущностей; точные составы FK приведены ниже.

### Общие примитивы

| Таблица | Основные поля / ключ | Для чего |
|---|---|---|
| `unit` | `code PK`, `name`, `symbol` | Единица измерения |
| `brand` | `code PK`, `name` | Бренд товара; полный состав не определен |
| `property` | `code PK`, `name`, `kind`, `unit_code FK`, `multiple` | Определение свойства и правила значения |
| `property_option` | PK `(property_code, code)`, `name` | Справочные значения конкретного свойства |
| `option_extra` | FK на опцию, `code`, `kind`, `value_text`, `value_color`, `image_uuid FK` | Дополнение `TEXT`, `COLOR` или `IMAGE` |
| `image` | Существующий `uuid PK` | В опыте только заглушка ключа существующей таблицы изображений |

Опция не выделяется в отдельную сущность «цвет». Код иконки хранится в текстовом
дополнении. Изображение связано с существующей таблицей по ее ключу, не по
придуманному коду изображения.

### Тип и наследники

| Таблица | Основные поля / ключ |
|---|---|
| `product_type` | `uuid PK`, `name` |
| `type_product_property` | PK `(type_id, property_code)` |
| `type_variant_property` | PK `(type_id, property_code)` |
| `product` | `uuid PK`, `type_uuid FK`, `brand_code FK`, `name`, `description`, `status` |
| `variant` | `uuid PK`, `product_uuid`, `type_uuid`, `name`, `status` |
| `product_property` | PK `(product_uuid, type_uuid, property_code)` |
| `variant_property` | PK `(variant_uuid, type_uuid, property_code)` |
| `product_property_value` | PK `(product_uuid, type_uuid, property_code, position)`, шесть типизированных столбцов |
| `variant_property_value` | PK `(variant_uuid, type_uuid, property_code, position)`, те же столбцы |

У варианта нет самостоятельно выбранного типа. `variant.type_id` в этом варианте
схемы — техническое повторение типа его товара, подтвержденное составным FK:

```text
variant(product_uuid, type_uuid)
  → product(uuid, type_uuid)
```

Это позволяет проверить назначение свойства варианту таким же способом, как
товару. Альтернатива консилиума: убрать `type_id` из Variant и добавить
`product_uuid` в его назначения для проверки через Product. Оба варианта
возможны; для исполняемого опыта выбран первый.

### Какие FK действительно запрещают чужое поле

У `product_property` две независимые составные связи:

```text
(product_uuid, type_uuid)  → product(uuid, type_uuid)
(type_uuid, property_code) → type_product_property(type_uuid, property_code)
```

Первая доказывает тип конкретного товара. Вторая доказывает, что свойство
включено именно в этот тип на уровне товара. Для варианта используются
`variant(uuid, type_uuid)` и `type_variant_property`.

FK назначения на поле типа имеет `ON DELETE CASCADE`. FK строки значения
на назначение тоже имеет `ON DELETE CASCADE`.

Нет универсальной пары `consumer_type + consumer_id`, которую невозможно
связать одним обычным FK с несколькими таблицами. Отдельные таблицы назначения
не ограничивают перечень свойств: их содержимое по-прежнему задает конструктор.

### Тип и кратность значения

В таблицах назначений и значений SQL-опыт дополнительно повторяет `kind`
и `multiple`. Это технические столбцы для ограничений; составные FK не дают
им расходиться с определением свойства. Пользователь их независимо не задает.

1. `CHECK` требует ровно один заполненный столбец значения.
2. Второй `CHECK` сопоставляет заполненный столбец с `kind`.
3. Частичный уникальный индекс запрещает вторую строку при `multiple=false`.
4. Составной FK `(property_code, value_option_code)` запрещает чужую опцию.
5. Уникальный индекс запрещает дважды выбрать одну опцию одному назначению.

`0` и `false` являются значениями. `NULL` во всех столбцах не считается
заполненным значением. Если значение не задано, строки значения нет.

Такое повторение нескольких технических полей делает DDL длиннее, но позволяет
проверять эти правила ограничениями БД. Альтернатива — более короткие таблицы
с проверяющими триггерами; тогда отдельно потребуется проверить обновления
родителей и конкурентные операции.

## 4. Как живет товар при изменении типа

Пусть три шампуня имеют один тип и разные pH: `5.5`, `6.0`, `7.0`.

| Действие | Изменение строк | Результат чтения |
|---|---|---|
| Создаем товар | Product, минимум один Variant, назначения и введенные значения в одной предполагаемой транзакции | Каждый товар получает собственные значения |
| Добавляем pH в тип | Новая строка `type_product_property` | У всех товаров этого типа появляется предусмотренное поле; значения автоматически не возникают |
| Вводим pH товара | Создается назначение, если его еще нет, и строка значения | Значение принадлежит конкретному товару |
| Удаляем pH из типа | Каскад удаляет назначения и их строки значений | pH исчезает у наследников и из поиска по их значениям |
| Добавляем pH снова | Новая строка поля, старых назначений и значений нет | Прежние значения не возвращаются |

Предполагаемое чтение начинается с полей актуального типа, затем делает
`LEFT JOIN` к назначениям и значениям товара. Поэтому добавление поля
не требует массово вставлять пустые значения во все товары. Конкретное
отображение незаполненной характеристики на витрине остается открытым.

Составной ключ повторно включенного поля может совпасть с прежним. Это
не восстанавливает удаленные дочерние строки. Однако старая открытая форма
может прислать прежнее значение уже новому включению того же свойства:
для этого отдельно нужен контракт проверки актуальности формы. Сам каскад
не решает гонку между изменением типа и сохранением формы.

### Архивирование товара и варианта

Прямое уточнение пользователя: Product и Variant никогда не удаляются,
а помечаются архивированными. В SQL добавлен `archived_at` только как
экспериментальный способ хранения отметки. Выбор между отметкой, статусом
и полным автоматом состояний не утвержден этим техническим примером.

Само архивирование выполняется обновлением записи и сохраняет идентификатор,
принадлежность варианту/товару, назначения и значения. Внешние ключи на Product
и Variant используют RESTRICT вместо каскада удаления владельца. Дополнительно
триггеры опыта отклоняют DELETE и TRUNCATE обеих таблиц. Права production-роли
и защита от административного отключения ограничений этим опытом не определены.

Каскад от удаленного поля типа к назначениям и значениям остается. Архивирование
не означает создание отдельной замороженной структуры. Автоматическое изменение
статусов вариантов при архивировании товара, восстановление, правила редактирования
архива и наличие хотя бы одного неархивированного варианта остаются открытыми.

Ранее найденный контрпример двух конкурентных физических удалений Variant
отозван как неприменимый к уточненной модели: эти операции теперь запрещены.
Проверка при создании Product считает существующие строки Variant; она не
является проверкой числа неархивированных вариантов.

## 5. Примеры в границах сервиса товаров

| Пример | Тип | Конкретные наследники |
|---|---|---|
| Майка | Общие свойства товара и структура свойств варианта | Товар «Майка», варианты «Синяя» и «Зеленая», у каждого собственные значения |
| Штаны | Собственный набор полей товара и подтипа | Товар «Штаны», варианты «Черные» и «Белые» |
| Телевизор | Свойства модели и структура варианта | Товар и минимум один реальный вариант |
| Шампунь | Общие свойства товара и свойства аромата | Три товара одного типа с разными значениями pH; ароматы — варианты |

Примеры используют одинаковые таблицы. Различаются поля типов, выбранные
определения свойств и значения конкретных наследников. Размерная детализация
учета, остатки, резервы, цены и заказы относятся к отдельному сервису и здесь
не проектируются. Категория отсутствует в проектируемом Product согласно RFC;
таблицы категории другого сервиса здесь не определяются.

## 6. Спор консилиума и принятый для проверки вариант

| Вопрос | Предложения и проверка | Итог эксперимента |
|---|---|---|
| Одна таблица всех назначений или отдельные | Catalog предложил nullable Product/Variant FK + XOR; Schema указал дополнительные проверки уровня и изменения владельца | Отдельные назначения и значения дают более явные составные FK |
| Как проверить тип варианта | Тип через Product с дополнительной ссылкой в назначении либо технический `type_id` в Variant | Выбран второй для меньшего числа переходов; самостоятельного типа варианта нет |
| Обязательный первый вариант | Отложенная проверка наличия дочерней записи при создании | Проверена; физическое удаление любого Variant запрещено. Предыдущее возражение о конкурентных DELETE после уточнения жизненного цикла неприменимо |

Консилиум не голосовал за изменение принятых требований. Его задача здесь —
предложить физические связи и обнаружить случаи, где они не обеспечивают правило.

## 7. Что проверено исполнением

Файлы: [схема](experiments/product-constructor/schema.sql),
[проверки](experiments/product-constructor/checks.sql),
[известные пробелы](experiments/product-constructor/known-gaps.sql).

PostgreSQL 16.15, отдельный временный кластер; режим single-user. Создание схемы
прошло без SQL-ошибок; итог проверок: `passed_checks = 34`, `all_passed = true`.
Проверки отрицательных сценариев проверяют ожидаемый SQLSTATE, а не просто
принимают любую ошибку за успех.

Проверены:

- разные значения трех товаров одного типа и поиск по диапазону;
- множественный выбор, одиночное значение, `0`, `false`;
- отказ для чужого типа, отсутствующего поля типа и неверного типа варианта;
- отказ для чужой опции, опции числового свойства, подмены кратности;
- отказ для двух заполненных столбцов, строки со всеми `NULL` и повторного
  выбора опции; пустой текст `''` этой проверкой не запрещается;
- отказ при удалении используемого определения/опции и смене используемого типа значения;
- запрет создания товара без варианта; запрет DELETE/TRUNCATE товара и любого варианта;
- сохранение записей и значений при архивировании товара и варианта;
- добавление поля к существующим товарам без выдумывания значений;
- каскад для товара и варианта; сохранность другого типа, определений, товаров и вариантов;
- отсутствие восстановления старых значений при повторном добавлении;

Это не E2E витрины и не проверка действующих сервисов. Нет доказательства
корректности индексов под реальной нагрузкой, конкурентных записей, обновления
поискового индекса, интеграционных событий или миграции.

## 8. Найденные пробелы и предлагаемые способы закрыть

| Пробел | Доказательство / статус | Что требуется |
|---|---|---|
| Единицу свойства можно изменить при существующих значениях | SQL-опыт сменил `cm` на `m`; проверка в `known-gaps.sql`, изменения откатили | Защита семантики определения при использовании; согласовать допустимость изменения до использования |
| Полный жизненный цикл архива | Принят запрет физического удаления, остальные переходы еще не определены | Согласовать состояния, восстановление, поведение дочерних вариантов и минимум неархивированных вариантов |
| Сохранение старой формы после удаления и повторного включения поля | Следует из повторяемого составного ключа | Контракт актуальности формы; не путать его с замороженными версиями типа |
| Идентификаторы неизменяемы после появления внешних потребителей | Локальные FK блокируют часть изменений, но не знают про отчеты и внешние ссылки | Явная политика изменения кодов, включая отсутствие локальных ссылок после удаления поля |

Ошибка запуска обычного временного PostgreSQL: sandbox запретил создание
Unix-сокета (`Operation not permitted`). Поэтому выполнены проверки в single-user
режиме; два конкурентных соединения не проверены. Работающие сервисы и БД не
подключались и не менялись.

Эти пробелы не опровергают разделение «определение → поле типа → назначение →
значения». Они опровергают более сильное предположение, что одних обычных FK
достаточно для всех правил системы. Ссылочная целостность, минимальное количество
дочерних записей и неизменность смысла свойства требуют разных ограничений.

## 9. Отличия от текущей реализации

Сверено по моделям БД, а не по интерфейсу:

- Сейчас ProductProperty/VariantProperty ссылаются прямо на Property, хранят
  строковый `value` и одну `option_uuid`. Нет проверенной здесь цепочки через
  поле типа и дочерние строки значений.
- PropertyOption сейчас имеет UUID PK и UNIQUE(propertyUuid, code). Составной
  кодовый PK в опыте — предлагаемая замена, не уже существующее ограничение.
- Сейчас metadata опции допускает ICON и file UUID; целевой RFC использует
  TEXT/COLOR/IMAGE с прямой ссылкой на таблицу изображения.

## 10. Как повторить опыт

Только в новом временном кластере PostgreSQL 16, не в рабочей БД:

```bash
experiment_dir=$(mktemp -d /tmp/sellgar-constructor-proof.XXXXXX)
/usr/lib/postgresql/16/bin/initdb -D "$experiment_dir/data" -A trust --no-locale --encoding=UTF8
/usr/lib/postgresql/16/bin/postgres --single -D "$experiment_dir/data" -j postgres < agent/docs/experiments/product-constructor/schema.sql > "$experiment_dir/schema.log" 2>&1
/usr/lib/postgresql/16/bin/postgres --single -D "$experiment_dir/data" -j postgres < agent/docs/experiments/product-constructor/checks.sql > "$experiment_dir/checks.log" 2>&1
/usr/lib/postgresql/16/bin/postgres --single -D "$experiment_dir/data" -j postgres < agent/docs/experiments/product-constructor/known-gaps.sql > "$experiment_dir/gaps.log" 2>&1
rg -n 'ERROR|FATAL|passed_checks =|all_passed =' "$experiment_dir/schema.log" "$experiment_dir/checks.log" "$experiment_dir/gaps.log"
```

Single-user PostgreSQL может завершиться с нулевым exit code при SQL-ошибках:
нужно проверять логи и итоговый счетчик. Последний файл намеренно воспроизводит
возможность смены единицы свойства в транзакции с откатом. Его успешное
исполнение подтверждает этот пробел, а не корректность такого изменения.
