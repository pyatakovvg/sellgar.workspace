# Тесты, ревью и последовательный рефакторинг

Чистота теста важна не меньше числа тестов: непонятный или нестабильный тест не даёт безопасно менять production-код. Однако тестирование — способ проверить контракт, а не ритуал вокруг каждого private helper.

## TEST — качество тестов

- **TEST-1 — наблюдаемый контракт.** Формулируй тест через вход, действие и результат, который важен потребителю. Проверка private вызовов оправдана лишь тогда, когда порядок/число вызовов и есть контракт.
- **TEST-2 — ясный сценарий.** По имени и подготовке должно быть понятно, какую ветку защищает тест. Один тест может иметь несколько assertions для одного связного результата; не дроби сценарий ради правила «один assert».
- **TEST-3 — независимость.** Тест не полагается на порядок запуска других тестов, общий изменяемый fixture или оставшиеся ресурсы. Управляй временем, случайностью и внешними ответами там, где они влияют на результат.
- **TEST-4 — повторяемость.** Падающий тест должен указывать на изменение кода или контракта, а не на гонку тестовой среды. Флейк не лечи произвольной задержкой; найди неуправляемое событие.
- **TEST-5 — подходящий уровень.** Unit проверяет локальное правило; contract — границу producer/consumer; integration — совместную работу; end-to-end/manual — пользовательский путь и платформенный эффект. Не требуй end-to-end для чистого преобразования и не выдавай unit за доказательство всей системы.
- **TEST-6 — значимые ветви.** Успех, отказ, отсутствие данных, границы диапазона, повтор, отмена и конкуренция проверяются по реальному риску, а не по фиксированному списку для каждой функции.
- **TEST-7 — тестовые данные.** Fixture должен соответствовать действующему контракту. Не ослабляй production-валидацию, чтобы упростить тест; не собирай чрезмерный объект, если проверяется одно правило.
- **TEST-8 — простота теста.** Предпочитай явную подготовку существенных данных и результат над глубокой иерархией helpers, которая скрывает причину провала.

## REF — последовательный рефакторинг

1. **Назови цель.** «Улучшить код» недостаточно. Укажи конкретное препятствие: добавление поля требует править N мест; ошибка теряет причину; два процесса делят lifecycle; вызов скрывает эффект.
2. **Зафиксируй поведение.** Найди существующие tests и реальные потребители. Если теста нет, выбери минимальную проверку до правки. Для визуального/внешнего поведения запиши воспроизводимый сценарий и наблюдение.
3. **Определи границу.** Что можно изменить без смены публичного контракта? Что требует согласования? Не называй изменение поведения «рефакторингом».
4. **Работай проверяемыми шагами.** Переименование, извлечение, перемещение и изменение зависимостей лучше разделять, если это помогает понять diff и найти регрессию. Не копируй старую реализацию рядом с новой на неопределённый срок.
5. **Удаляй заменённое.** После переключения всех разрешённых потребителей убери мёртвый путь, лишние параметры, комментарии и временные адаптеры. Если сохранить старый контракт действительно нужно, это явное решение о совместимости.
6. **Повтори проверку.** Сравни публичное поведение, ошибки, побочные эффекты и порядок операций до/после. Прогони проверки пакета и целевой сценарий. Сообщи, что не удалось проверить.

TDD может помочь при чётком поведении, но не является единственным допустимым порядком работы. Красный тест должен отражать требование, а не фиксировать структуру, которую ты собираешься удалить.

## SMELL — сигналы для расследования, не автоматические нарушения

| Сигнал | Что подтвердить | Возможное направление |
| --- | --- | --- |
| Одно требование меняет много мест | Все места действительно реализуют одно правило? | Перенести правило к владельцу и оставить адаптацию у потребителей. |
| Один класс меняется по несвязанным причинам | Разные потребители, жизненные циклы или политики? | Разделить обязанности по причинам изменения. |
| Метод постоянно читает внутренности другого объекта | Это прозрачные данные или чужой защищённый инвариант? | Дать операцию владельцу инварианта; не оборачивать каждый getter. |
| «Универсальный» helper с флагами и ветками | Флаги представляют один алгоритм или несколько процессов? | Разделить процессы либо оставить параметризацию с ясным контрактом. |
| Повторяющиеся примитивы и строки | Есть ли одно понятие с едиными правилами валидации/формата? | Ввести смысловой тип, когда он предотвращает реальные ошибки. |
| Проверка состояния перед каждым вызовом | Есть ли скрытое требование порядка или допустимые состояния? | Сделать переход и инвариант частью контракта владельца. |
| Новый слой только делегирует старому | Есть ли собственная политика, lifecycle или внешняя граница? | Упростить путь; не сохранять прокладку из-за шаблона. |
| Комментарий объясняет порядок вызовов | Можно ли выразить порядок контрактом/API и тестом? | Уточнить ответственность; комментарий оставить для причины внешнего ограничения. |

## REVIEW — доказательное ревью

При явном запросе на аудит сначала укажи проверенную границу и режим (read-only). Для каждого замечания используй структуру из `SKILL.md`: точное место, факт, последствие, правило, владелец исправления, проверка. Приоритет определяется возможным последствием, а не длиной кода. Отдельно выведи:

- подтверждённые дефекты;
- архитектурные риски, для которых показан правдоподобный сценарий;
- гипотезы и способ их опровержения;
- проверки, которые не удалось выполнить.

Не заполняй ревью десятками стилистических замечаний, если они заслоняют ошибку контракта или потерю данных. Если нарушений нет, перечисли рассмотренные границы и проверенные сценарии, а не объявляй код «идеальным».
