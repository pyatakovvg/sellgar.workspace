# Разборы решений

Примеры намеренно не привязаны к языку, UI-фреймворку или репозиторию. Это модели рассуждения: перед реальным исправлением проверь действующий контракт и всех потребителей. Вывод по похожему коду без этой проверки остаётся гипотезой.

## 1. Флаг меняет смысл операции

```text
updateAccount(change, dryRun):
  account = repository.read(change.id)
  account.apply(change)
  if not dryRun:
    repository.save(account)
    notifier.send(account)
  return account
```

**Не делай вывод только по наличию boolean.** Посмотри места вызова: один caller показывает пользователю прогноз без записи; второй ожидает запись и уведомление. Проверь, возвращается ли в обоих случаях один и тот же тип результата и может ли caller отличить сохранённое состояние от прогноза. Это конкретный риск: имя `updateAccount` обещает изменение даже при `dryRun=true`.

**Варианты.** Если это два самостоятельных use case, выдели `previewAccountChange` и `applyAccountChange`; общий чистый расчёт оставь у владельца правила. Если контракт действительно определяет единый update с режимом исполнения, сохрани одну операцию, но сделай режим и результат явными. Выбирай по потребителям и публичному контракту, не по количеству методов.

**Проверка.** Прогноз не записывает и не уведомляет; применение записывает ровно один раз; при ошибке сохранения уведомление не отправляется. Изменение имени/сигнатуры сопровождается обновлением всех callers в разрешённой области.

## 2. Валидация одной формы, использование другой

```text
raw = transport.fetch()
validated = schema.parse(raw)
return raw
```

**Факт.** Проверен `validated`, а наружу возвращается `raw`. Если `parse` приводит типы, удаляет лишние поля или создаёт новый объект, вызывающий код получает не тот результат, который проверялся. Ошибка может не проявиться на идеальном fixture.

**Владелец.** Адаптер, читающий внешний источник, отвечает за преобразование и проверку на этой границе. Он возвращает проверенную форму либо явно преобразует её в принадлежащую следующему слою модель. Другой слой не должен повторно догадываться о свойствах внешнего формата.

**Проверка.** Подай вход с преобразуемым значением и лишним полем. Убедись, что результат соответствует проверенному контракту; отдельно проверь ошибку невалидного входа с сохранённой причиной. Не ослабляй схему, чтобы старый fixture стал зелёным.

## 3. Поздний ответ перезаписывает новый

```text
search("a")  # запрос A
search("ab") # запрос B
response(B)  # показываем B
response(A)  # старый A перезаписывает B
```

**Инвариант.** Показанный результат соответствует последнему принятому поисковому запросу. Сначала найди владельца этого решения: контроллер поиска, сервис или хранилище, но не несколько независимых consumers.

**Варианты.** Отменить A при новом запросе; версионировать запросы и применять только актуальный результат; сериализовать операции, если порядок завершения является предметным требованием. Таймер после ответа лишь меняет вероятность гонки. Отмена без проверки актуальности может быть недостаточной, если источник уже прислал ответ.

**Проверка.** Контролируемо заверши B раньше A; затем заверши A и убедись, что состояние осталось B. Проверь ошибку A после успеха B, отмену и освобождение ресурсов владельца. Stress-тест полезен дополнительно, но не заменяет этот конкретный порядок.

## 4. Замечание в ревью без доказательств

**Неполезно:** «Класс большой, нарушен SRP; вынести в три класса». Это не называет ни независимых причин изменения, ни последствия, ни границы.

**Проверяемо:** «Один объект формирует цену и форматирует её для PDF. Новый налоговый порядок меняет расчёт, новый дизайн PDF меняет форматирование; обе правки затрагивают один класс и его общие поля. Расчёт должен оставаться у владельца цены, PDF-представление — у экспортера. Проверь сумму по существующим примерам и отдельно вид PDF после переноса». Если анализ кода не подтвердил две причины изменения, такое замечание преждевременно.

Ревью не должно принимать красивый рассказ за факт. Для реального проекта добавь точные файл и строку, укажи потребителей и раздели подтверждённое наблюдение от предполагаемого будущего изменения.

## 5. Освобождение старого владельца затрагивает нового

Реестр сохраняет `key → registration`. Клиент получает функцию освобождения. Старую регистрацию заменили, затем её клиент завершился и вызвал `delete(key)`. Удалена уже новая регистрация.

**Инвариант:** клиент освобождает только принадлежащую ему регистрацию. Сравнение текущей регистрации с захваченной identity либо отдельный lease делает это явным. Если несколько клиентов намеренно разделяют ресурс, нужен контракт совместного владения, а не случайный счётчик.

**Неверное исправление:** отложить очистку на несколько миллисекунд или перед очисткой лишь проверить существование key. Это не устанавливает принадлежность и не исключает ошибочный порядок.

**Проверка:** создать A, заменить на B, освободить A, использовать B; повторить освобождение A. B остаётся доступен. Изменение не должно заставлять caller управлять внутренностями реестра.

## 6. Изменяемая ссылка выдана за снимок

Источник выдаёт один объект `status`, меняет его поля и уведомляет подписчиков. Потребитель сравнивает identity последнего значения, пропуская неизменившийся объект. Уведомление произошло, но отображение осталось прежним.

**Выбор контракта:** либо источник публикует стабильные неизменяемые снимки с новой identity при изменении, либо явно предлагает live-object с отдельным механизмом наблюдения. Нельзя обещать первое, реализуя второе. Это применимо к UI, кэшу и event-driven интеграции.

**Неверное исправление:** запретить оптимизации каждому consumer или принудительно обновлять всё дерево. Это переносит скрытое знание об источнике во всех потребителей.

**Проверка:** новый снимок отражает изменение, старый не мутирует; повторное чтение без изменения стабильно. Исправление не меняет владельца предметного состояния.

## 7. Два адаптера похожи, но объединять всё нельзя

Два транспорта повторяют проверку прав, но по-разному подтверждают доставку. Общая проверка прав может иметь одного владельца; подтверждение должно остаться у адаптеров согласно гарантиям транспорта.

**Неверное исправление:** объединить файлы в универсальный класс с флагом транспорта, поместив оба протокола рядом, либо протащить SDK одного транспорта в предметный слой ради повторного использования.

**Проверка выбора:** новое правило прав меняется в одном месте и действует для обоих; сбой подтверждения одного транспорта не меняет семантику другого. Если одинаковый код пока выражает разные правила, сохранить отдельные реализации — обоснованный результат.
