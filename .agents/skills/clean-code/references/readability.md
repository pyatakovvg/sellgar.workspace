# Имена, функции, комментарии, форматирование

Применяй правила к коду в переданной области, не требуя массового переименования соседних API. В ревью указывай ID правила и конкретный вызов, который становится понятнее или безопаснее после исправления.

## NAME — имена

- **NAME-1 — намерение.** Имя операции отвечает, какое действие происходит и над чем; имя значения — что это за значение и в какой роли оно используется. `process`, `data`, `manager`, `handler` и подобные слова сами по себе не ошибка, но не должны быть единственной информацией о назначении.
- **NAME-2 — отсутствие дезинформации.** Не называй значение списком, если контракт не гарантирует коллекцию; не используй слова `cache`, `transaction`, `atomic`, `safe`, если заявленные свойства не обеспечены. При ревью сравни имя с фактическим поведением на всех ветках.
- **NAME-3 — осмысленные различия.** `item`, `itemInfo`, `itemData` различаются только написанием, если у них нет разных ролей. Назови роли (`request`, `validatedInput`, `result`) или убери лишнюю промежуточную форму.
- **NAME-4 — единый словарь.** Одно понятие внутри контракта называй одним термином; не смешивай `fetch`, `load`, `resolve`, `read` как случайные синонимы. Разные действия не называй одним словом только потому, что они возвращают одинаковый тип.
- **NAME-5 — контекст без шума.** Локальному `count` может хватить контекста; публичному `timeout` часто нужны единица измерения и предметная область. Не повторяй имя модуля во всех локальных сущностях, если оно уже очевидно из границы.
- **NAME-6 — читаемость в вызове и поиске.** Проверь имя на месте использования, а не только в определении. Исключи каламбуры, необъяснённые сокращения и число/букву, которые трудно найти поиском. Устоявшиеся термины предметной области сохраняй.

## FUNC — функции

- **FUNC-1 — одна связная работа.** Объясни функцию одним предложением без «и ещё». Несколько шагов одного алгоритма остаются одной работой, если их порядок образует единый контракт. Размер — сигнал для анализа, не автоматическое нарушение.
- **FUNC-2 — уровень абстракции.** Основной путь показывает решения; детали формата, протокола или перебора не должны заслонять его. Извлечённая функция полезна, когда её имя заменяет сложность понятным действием, а не добавляет прыжок по файлам.
- **FUNC-3 — ясные аргументы.** По сигнатуре и вызову должно быть видно, какие входы требуются и какие выходы получаются. Не передавай не связанный с операцией «мешок опций» или скрытый глобальный вход. Количество аргументов само по себе не нарушение.
- **FUNC-4 — режимы.** Boolean-флаг подозрителен, когда выбирает два разных действия, разных эффекта или результата. Тогда сравни два названных метода с одной параметризованной операцией. Флаг, уточняющий единую операцию, допустим.
- **FUNC-5 — команда и запрос.** Запрос не должен незаметно изменять предметное состояние или инициировать I/O, если контракт обещает чтение. Команда должна явно сообщать об эффекте и результате. Уточни контракт, если ленивое чтение или кеширование действительно требует эффекта.
- **FUNC-6 — локальность управления.** Сделай порядок зависимых шагов, ранние выходы и причины ветвления видимыми. Не прячь ключевой переход в цепочке callbacks/helpers. Отдельный helper не оправдан, если чтение целого стало труднее.
- **FUNC-7 — изменение входа.** Не мутируй вход молча, когда вызывающий код ожидает значение. Если in-place изменение часть контракта, обозначь его в API и проверь всех потребителей. Возврат нового значения предпочтителен, когда снижает скрытую связность.

### Быстрая проверка функции

Прочитай 2–3 реальных вызова и ответь: «Что ожидает caller?», «Какие эффекты реально происходят?», «Какие ветви важны?», «Что можно назвать без потери контекста?». Предлагай выделение функции только после этой проверки. Например, `submit(document, true)` может скрывать выбор между «проверить» и «сохранить»; это не доказательство без просмотра обеих веток.

## COMMENT — комментарии

- **COMMENT-1.** Комментарий добавляет причину, ограничение внешнего контракта, нетривиальный инвариант или последствия нарушения. Пересказ соседней строки убирай после улучшения имени или структуры.
- **COMMENT-2.** Не оставляй комментарий, противоречащий коду. При изменении условия, алгоритма или API проверь связанные комментарии, примеры и документацию.
- **COMMENT-3.** `TODO` обозначает конкретное незавершённое действие с владельцем или контекстом, а не бесконечное обещание. Не используй комментарий, чтобы узаконить неработающий путь.
- **COMMENT-4.** Публичный контракт может требовать документации даже при ясном имени: семантика ошибок, границы значений, порядок вызовов и ownership ресурсов не всегда выражаются типом.

## FORMAT — расположение и формат

- **FORMAT-1.** Соблюдай formatter и соглашение репозитория. Не делай массовую переформатировку в поведенческой правке, если она скрывает diff.
- **FORMAT-2.** Размещай связанные части рядом в порядке чтения: публичный путь, затем детали, необходимые для него. По возможности сокращай прыжки между файлами для понимания одного небольшого алгоритма.
- **FORMAT-3.** Пустые строки, группировка и порядок объявлений должны показывать смысловые границы, а не заменять отсутствующую архитектурную границу.

## Типичные ложные выводы

- «Функция длиннее N строк — разбить» не устанавливает, что новый набор функций будет яснее.
- «Каждый метод должен быть без параметров» не учитывает явный контракт и зависимость от контекста.
- «Все комментарии вредны» теряет информацию о внешнем ограничении и причине решения.
- «Имя непонятно мне» требует сравнения с предметным словарём и местами вызова, прежде чем объявлять дефект.
