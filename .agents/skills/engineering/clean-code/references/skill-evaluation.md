# Проверка полезности скилла

Используй при изменении скилла или запросе оценки его эффективности. Валидатор структуры проверяет файлы/frontmatter, но не качество решений.

## Сценарии

Подбери небольшой набор независимых задач с разными последствиями: локальная читаемость, граница данных, освобождение ресурсов, несколько реализаций контракта, системный аудит. Используй реальные разрешённые примеры либо небольшие изолированные fixtures. Не все задачи обязаны содержать дефект: нужен пример, где правильное решение — не вводить абстракцию и не менять код.

Не закрепляй названия проекта, библиотеки или конкретный прошлый баг в универсальных правилах. Примеры различаются предметной областью, а проверяемая способность остаётся общей.

## Выполнение и оценка

Проверяющему передаются запрос, исходные материалы и скилл, без готового диагноза. Независимый прогон полезен, если доступен и разрешён; повтор автором после просмотра решения помечай как неслепую проверку.

Оцени не совпадение формулировок, а решения:
- Сохранены ли запрос и охват, указаны ли ограничения?
- Есть ли воспроизводимая связь «факт → последствие»?
- Найден ли правильный владелец исправления без расширения разрешений?
- Различены ли дефект, риск, среда и неясный контракт?
- Отвергнуты ли неподтверждённые замечания и ненужные абстракции?
- Получилась ли проверяемая рекомендация, а при реализации — сохранённый соседний контракт?

Для каждого провала укажи, какое решение не направлялось инструкцией. Если инструкция уже была ясной, не добавляй её дубликат: это может быть ошибка исполнения, а не недостаток содержания. После изменения повтори проблемный сценарий и соседний, в котором чрезмерно жёсткое правило повредит.

Без сопоставимого прогона с/без скилла не назначай процент эффективности. Достаточный результат — конкретные примеры улучшенных решений, ложных выводов и оставшихся пробелов.
