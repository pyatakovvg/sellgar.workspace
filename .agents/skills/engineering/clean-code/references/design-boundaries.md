# Данные, объекты, классы и границы

Выбирай модель по тому, как будут меняться требования. Не объявляй процедурный код хуже объектного: оба подхода имеют цену, а смешение их обязательств в одной сущности часто дороже каждого по отдельности.

## DATA — данные и поведение

- **DATA-1 — значение или объект.** Простая форма данных раскрывает структуру для передачи/преобразования. Объект защищает инвариант и предоставляет действия. Не добавляй getters/setters только ради вида «инкапсуляции», если внешние потребители всё равно управляют внутренним порядком операций.
- **DATA-2 — инвариант.** Определи, какие состояния допустимы, кто создаёт значение и где оно проверяется. Если изменение поля требует синхронно поправить другие поля, операция должна находиться у владельца этого инварианта либо у явно названного координатора.
- **DATA-3 — транспортная форма.** DTO, сообщение и API-response описывают форму передачи, а не автоматически становятся доменной моделью. Не тащи внешние имена, временные поля и формат сериализации через весь код без причины.
- **DATA-4 — отсутствие значения.** Выбери представление отсутствия (`optional`, `null`, result, исключение) согласно контракту. У caller должен быть однозначный способ отличить «нет данных» от «операция не удалась». Не добавляй декоративную проверку `null` в каждом слое вместо определения границы.
- **DATA-5 — преобразование.** Укажи исходную и целевую формы и владельца преобразования. Не валидируй одну форму, а затем отправляй непроверенную исходную. Mapper нужен для реального преобразования смысла или структуры, не для копирования одинаковых полей по привычке.

## CLASS — ответственность и связность

- **CLASS-1 — причина изменения.** Перечисли независимые требования, которые могут заставить менять класс/модуль. Если они принадлежат разным владельцам или жизненным циклам, раздели обязанности. Несколько методов одного use case не являются несколькими ответственностями.
- **CLASS-2 — связность.** Поля и методы должны поддерживать один понятный контракт. Если две группы методов почти не используют общее состояние, проверь необходимость разделения; если разделение требует постоянной пересылки половины состояния, граница может быть неверной.
- **CLASS-3 — сокрытие решений.** Публичное API должно открывать нужные операции, а не порядок манипуляций внутренними полями. Избегай длинной цепочки доступа к внутренностям чужого владельца; при этом fluent API или честная структура данных сами по себе не нарушение.
- **CLASS-4 — зависимость.** Направляй зависимость к владельцу контракта. Вводи интерфейс/порт там, где есть реальная граница, подмена, политика или независимое изменение; не создавай интерфейс к каждому классу автоматически.
- **CLASS-5 — создание.** Явно реши, кто создаёт объект и кто им пользуется. Сложная сборка зависимостей не должна повторяться в бизнес-операциях; composition root, фабрика или builder нужны лишь при соответствующей сложности и сроке жизни.
- **CLASS-6 — циклы.** Если два компонента требуют друг друга для создания или работы, найди смешанные обязанности или неверное направление зависимости. Lazy lookup не является самостоятельным архитектурным исправлением цикла.

## BOUND — внешние и внутренние границы

- **BOUND-1 — сторонняя библиотека.** Изолируй её API там, где смена, особая семантика или тестирование действительно затронут многие consumers. Не оборачивай всю библиотеку механическим proxy без собственной политики.
- **BOUND-2 — внешний контракт.** Проверь реальные входы, выходы, ошибки и lifecycle библиотеки/сервиса до проектирования адаптера. «Learning test» может зафиксировать спорное поведение зависимости; mock, придуманный по ожиданиям, этого не доказывает.
- **BOUND-3 — направление импорта.** Модуль не должен импортировать приватную реализацию соседнего владельца ради удобства. Публичный контракт и зависимости устанавливай там, где определена ответственность, а не там, где короче путь к файлу.
- **BOUND-4 — доверие.** Проверяй внешние данные при пересечении границы; внутри проверенной области не повторяй ту же валидацию на каждом шаге. Ошибки формата должны сохранять достаточный контекст для исправления или диагностики.
- **BOUND-5 — разделение решений.** Изменение UI, транспорта, хранения или стороннего SDK не должно само по себе менять предметное правило. Если правила реально зависят от платформы, вырази это явным контрактом, а не скрытым импортом.

## SYS — устройство системы

- **SYS-1.** Отдели конфигурацию и сборку системы от повседневного выполнения use cases. Это делает путь исполнения прослеживаемым и предотвращает повторную инициализацию по случайному вызову.
- **SYS-2.** Не выбирай архитектурную технологию «на будущее» без подтверждённой границы. Оставляй возможность замены через ясный контракт, когда стоимость такого контракта оправдана текущим риском.
- **SYS-3.** Проверяй систему через реальные границы взаимодействия, а не только через внутренние unit-тесты. При спорном поведении сторонней зависимости сначала воспроизведи её контракт.

## Как принять спорное решение

Для двух вариантов покажи: (1) кто теперь владеет инвариантом, (2) что меняется при новом требовании, (3) какие зависимости появляются, (4) какие состояния становятся невозможными, (5) как доказать контракт. Если один вариант просто переносит те же поля и условия в дополнительный слой, он обычно не улучшает архитектуру.

Не сообщай «нарушен SRP» без двух конкретных независимых причин изменения. Не сообщай «нарушен закон Деметры» лишь потому, что в коде есть точка после точки: покажи, где caller получает знание о внутреннем устройстве чужого владельца.
