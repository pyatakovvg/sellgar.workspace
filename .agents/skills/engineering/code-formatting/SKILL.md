# Оформление кода

## Источник правил

Прочитай formatter/linter configuration, editor settings и ближайшие инструкции целевого пакета. Определи, какие правила реально проверяются, а какие существуют только в тексте. Не добавляй язык, инструмент или dependency только потому, что они есть в другом проекте.

Если автоматизированного правила нет, установи единое соглашение в разрешённой границе. При прямой задаче на оформление закрепи переносимые требования в существующем formatter/linter и локальной документации; не пиши собственный parser вместо подходящего готового правила.

## Читаемая структура

- Соблюдай единые отступы, переносы и завершение строк, заданные инструментами пакета.
- Отделяй импорты от объявлений. Группируй их по принятому смыслу: imports с эффектами, стандартная библиотека, внешние зависимости, внутренние публичные packages, относительные файлы. Учитывай порядок исполнения side-effect imports.
- Отделяй методы друг от друга пустой строкой. Декораторы и документацию сохраняй вместе с их объявлением; связанные overload signatures держи цельным контрактом.
- Внутри функции показывай пустыми строками подготовку данных, существенный эффект и возврат. Не разделяй каждую строку механически; связные объявления образуют блок.
- Располагай публичный сценарий и его детали в порядке чтения. Не вводи искусственные разделители и комментарии, пересказывающие синтаксис.

Применяй [readability](../clean-code/references/readability.md) для смысловых границ. Formatter может исправлять whitespace, не замечая отсутствующих групп импортов или смешения обязанностей.

## Проверка

В аудите выполняй check-only. В разрешённой реализации запускай autofix только для целевых файлов/пакетов; исключай vendor, nested repositories и generated output по их границам. Commit-only задача не является запросом на переформатировку.

Посмотри diff и проверь, что порядок и структура не изменили поведение. Для массовой обработки полезно сравнение синтаксического дерева и релевантные существующие checks; отдельные тесты на пробелы не нужны. Если изменение imports влияет на side effects, проверь соответствующий consumer.

Сообщи, какие правила закреплены, чем проверяются и где остаётся ручная проверка. Не называй весь код оформленным по одному успешному formatter check, если часть файлов не входит в его scope.
