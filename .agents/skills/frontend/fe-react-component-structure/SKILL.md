# React-компонент

## Область действия и приоритет

- Применяй этот скилл только к React-компонентам web frontend и их локальным детям.
- Не применяй его к backend rendering, mobile, React Native, infrastructure и server-side packages. Наличие React-подобной component-модели за пределами web frontend не расширяет область скилла.
- В cross-layer задаче проверяй и изменяй по этому скиллу только frontend-компоненты. Остальные части передавай соответствующему профильному маршруту или скиллу.
- Применяй правила к каждому React-компоненту в переданной границе и рекурсивно к его локальным детям, но не оценивай этим скиллом архитектуру `view`, экранное дерево и application data flow.
- Не определяй этим скиллом структуру mediator/view, application data flow, controller, HTTP, Context, Provider и дерева экранов. Для них используй отдельный скилл.
- Считай этот `SKILL.md` первичным целевым стандартом компонента: legacy-код, комментарий или старый `AGENTS.md` не легализуют исключение.
- При разработке и рефакторинге обновляй только противоречащие правила в `AGENTS.md` реально затронутого компонента и непосредственных детей. При read-only аудите не изменяй документы и указывай противоречие в отчёте.
- Не копируй legacy-стиль вопреки правилам скилла.
- Для любого оговорённого исключения остановись до изменения, покажи необходимость, альтернативы и последствия, затем запроси явное подтверждение разработчика.

## Алгоритм

1. Определи владельца, непосредственных потребителей, публичный контракт и базовый HTML- или React-компонент.
2. Определи роль: локальный композиционный родитель, финальная логическая композиция отображения/управления, элемент коллекции, абстрактный компонент `library/design` или фабричный компонент.
3. Проверь props, управляемое состояние, refs, hooks, события, JSX, стили, фасад и локальные функциональные роли.
4. Составь минимальное целевое дерево. Не создавай файлы и каталоги заранее.
5. Реализуй изменение вместе с непосредственными потребителями контракта и затронутыми `AGENTS.md`.
6. Если пользователь запросил только аудит, не изменяй код и выведи отчёт по разделу `AUDIT`.

## BASE — объявление компонента

- **BASE-1.** Используй только function components. Class components запрещены.
- **BASE-2.** Импортируй React через `import React from 'react'`. Не используй именованные импорты из `react`.
- **BASE-3.** Обращайся ко всем React API через namespace: `React.FC`, `React.useState`, `React.ReactNode`, `React.Ref`.
- **BASE-4.** Объявляй компонент через `const` и `React.FC`:

```tsx
export const Button: React.FC<IProps> = (props) => {
  return <button />;
};
```

- **BASE-5.** Используй только именованный экспорт. `export default` запрещён.
- **BASE-6.** Один `*.tsx` production-файл объявляет один React-компонент. Локальные чистые helpers и константы допустимы; именованное тело и отдельный HOC-result из `REACTIVE-3` являются одним компонентом и разрешённым исключением.
- **BASE-7.** Не объявляй компонент внутри другого компонента или callback.
- **BASE-8.** Не создавай пустой `IProps`, если props отсутствуют. В этом случае используй `React.FC`.
- **BASE-9.** Называй module-level константы через `UPPER_SNAKE_CASE`, остальные значения — через `camelCase`.
- **BASE-10.** Не добавляй явный тип там, где TypeScript точно выводит его. Указывай конкретный тип, когда вывод неточен, расширяется или теряет контракт.

## STR — структура

- **STR-1.** Компонент является каталогом. Каталог и файл называй в `kebab-case`, компонент — в `PascalCase`:

```text
button/
  default.module.scss
  index.ts
  button.tsx

main-layout/
  index.ts
  main-layout.tsx
```

- **STR-2.** Фасад `index.ts` содержит явный реэкспорт: `export { Button } from './button'`. `export *` запрещён.
- **STR-3.** Размещай дочерний компонент непосредственно в каталоге родителя, без промежуточного `components/`:

```text
main-layout/
  header/
    index.ts
    header.tsx
  main-layout.tsx
  index.ts
```

- **STR-4.** Не экспортируй внутреннего ребёнка из фасада родителя. Родитель импортирует его через локальный фасад `./header`.
- **STR-5.** Не используй плоскую структуру для самостоятельных ролей:

```text
button/
  factory/
    button-state.factory.ts
  hooks/
    use-button-state.hook.ts
  mapper/
    button-props.mapper.ts
  reducer/
    button-state.reducer.ts
  serializer/
    button-state.serializer.ts
  index.ts
  button.tsx
```

- **STR-6.** Не создавай `index.ts` во внутренних каталогах `factory`, `hooks`, `mapper`, `reducer` и `serializer`. Импортируй внутренний файл напрямую.
- **STR-7.** Используй `.tsx` только для файла с JSX. Остальные файлы имеют расширение `.ts`.
- **STR-8.** Не создавай tests и stories для обычных React-компонентов. Stories допустимы только по отдельной явной задаче для UI kit.
- **STR-9.** Создавай `default.module.scss` для компонента с собственным визуальным root. Не создавай пустой stylesheet для фабрики или технического компонента без DOM-root.
- **STR-10.** Оставляй локального ребёнка приватным, пока у него ровно один владелец-потребитель в исходном коде. Несколько render instances одного владельца, включая `map`, не являются переиспользованием.
- **STR-11.** Если компонент импортируют два и более разных владельца, перенеси его в `library/design` как самостоятельную абстракцию. Не легализуй повторное использование глубоким импортом локального ребёнка.
- **STR-12.** Считай неиспользуемый локальный компонент, файл, фасад и CSS-класс нарушением. Перед удалением ищи потребителей по всему доступному проекту.
- **STR-13.** Не определяй этим скиллом размещение и имя архитектурных entrypoints вроде `*.view.tsx`, `module.tsx` и mediator. Применяй к их React-телу подходящие component rules, а структуру entrypoint передавай профильному view/application-скиллу.
- **STR-14.** После переноса или удаления файлов удали каждый ставший пустым каталог в затронутом исходном и целевом дереве, включая опустевшую цепочку родителей. Не оставляй каталог только потому, что Git его не отслеживает. Перед завершением явно проверь затронутую границу на пустые каталоги.

## PROP — props

- **PROP-1.** Объявляй props рядом с компонентом как внутренний `interface IProps`. Используй внутренний `type IProps` только для discriminated union, когда он запрещает несовместимые комбинации props, которые нельзя выразить одним interface. Не экспортируй props-контракт.
- **PROP-2.** Обращайся к значениям через `props.value`. Не деструктурируй props ради сокращения кода.
- **PROP-3.** Разрешай деструктуризацию параметра только для:
  - исключения собственных props перед `{...props}`;
  - проброса React 19 `ref`;
  - значений по умолчанию.
- **PROP-4.** Не создавай промежуточную конструкцию `const { value, ...props } = props`.
- **PROP-5.** Задавай default values только в параметре функции. Не используй `defaultProps` и локальные fallback-переменные:

```tsx
export const Button: React.FC<IProps> = ({
  loading = false,
  size = 'medium',
  ...props
}) => {
  return <button {...props} />;
};
```

- **PROP-6.** Определяй обязательность по смыслу. Необязательные flags вроде `loading?: boolean` приветствуются.
- **PROP-7.** Передавай boolean prop явно: `<Button loading={true} />`. Сокращение `<Button loading />` запрещено.
- **PROP-8.** Называй публичные boolean props в нативном стиле: `loading`, `active`, `disabled`, `open`. Для внутренних значений допустимы `isFocused`, `hasValue`; setter называй `setFocused`.
- **PROP-9.** Описывай string union и callback прямо в `IProps`, пока нет доказанной необходимости отдельного типа:

```tsx
interface IProps {
  size?: 'small' | 'medium' | 'large';
  onChange?: (value: string) => void;
}
```

- **PROP-10.** Не создавай механические callback-имена `onValueChange`, `onOpenChange`, `valueChange`. Используй смысловые пары: `value/onChange`, `open/onOpen`, `select/onSelect`.
- **PROP-11.** Определяй payload callback по уровню абстракции: нативный control сохраняет React event, смысловой компонент возвращает смысловое значение. При неоднозначности остановись и запроси решение.
- **PROP-12.** Используй `React.PropsWithChildren<IProps>` только если базовый props-контракт ещё не содержит `children` и компонент допускает необязательный children.
- **PROP-13.** Если children обязателен, объяви `children: React.ReactNode` в `IProps`. Не дублируй children, уже предоставленный базовым контрактом.
- **PROP-14.** Если props отсутствуют, не создавай `IProps`. Если единственный prop — необязательный children, используй `React.FC<React.PropsWithChildren>`.
- **PROP-15.** `IProps` остаётся в файле компонента. Если архитектуре крайне нужен общий объектный props-тип, остановись и запроси подтверждение. После подтверждения вынеси экспортируемый `IProps` в `<component>.types.ts` рядом с телом компонента; не экспортируй его из публичного фасада.
- **PROP-16.** `any` запрещён. Используй `unknown` с явным сужением. Считай `as` и non-null assertion `!` признаками плохого контракта; применяй только после обоснования и подтверждения.
- **PROP-17.** Используй `import type` для импортов, не существующих во время выполнения.
- **PROP-18.** Используй data и управляющие props для абстрактных переиспользуемых компонентов. Локальный компонент сам читает принадлежащие ему данные и обращается к готовому controller/context/framework-механизму; layout-родитель только размещает ребёнка. Для прямого контракта элемента коллекции применяй отдельное правило `PROP-20`.
- **PROP-19.** Не передавай локальному ребёнку данные или callbacks через props ради связывания с controller. Не прокидывай prop через композиционный узел, который сам его не использует. Не считай прямую передачу владельцем коллекции данных самому компоненту элемента prop drilling.
- **PROP-20.** Разрешай владельцу `map` передать непосредственно локальному компоненту элемента текущую сущность или модель: `<Product product={product} />`. Вместе с ней допустимы необходимые контракту коллекции `index`, производные flags и callbacks, если сам компонент элемента их использует и не передаёт дальше. Это контракт итерации, а не переиспользование или prop drilling; предпочитай готовую сущность повторному поиску по `id`.
- **PROP-21.** Передавай `index` только когда позиция является частью внешнего контракта коллекции, например пути поля динамической формы. Не используй его вместо стабильной идентичности. Если компонент элемента расслаивается и entity, index, flag или callback начинают проходить через промежуточные узлы, не строй цепочку props: укажи необходимость отдельного Context/Provider-решения вне этого скилла.
- **PROP-22.** Разрешай `as const` без согласования. Для остальных type assertions и non-null assertions сохраняй требования `PROP-16`.

## NATIVE — декорирование и нативный контракт

- **NATIVE-1.** Наследуй полный props-контракт декорируемого HTML-элемента и исключай `className` и `style`:

```tsx
interface IProps extends Omit<
  React.ButtonHTMLAttributes<HTMLButtonElement>,
  'className' | 'style'
> {
  loading?: boolean;
}
```

- **NATIVE-2.** При декорировании React-компонента используй `React.ComponentProps<typeof BaseComponent>` и также исключай `className` и `style`.
- **NATIVE-3.** Если собственный prop совпадает с нативным по имени, но отличается по смыслу или типу, сначала исключи его через `Omit`.
- **NATIVE-4.** Потребитель не вправе изменять `className` и `style` компонента.
- **NATIVE-5.** Отделяй собственные props в параметре и передавай оставшиеся props корневому элементу через `{...props}`.
- **NATIVE-6.** Максимально сохраняй нативные props, события и поведение. Не меняй нативные defaults без явного условия компонента.
- **NATIVE-7.** Если условие компонента переопределяет нативный prop, поставь вычисленное значение после `{...props}`.
- **NATIVE-8.** Для React 19 передавай ref как prop. Не используй `React.forwardRef`:

```tsx
interface IProps extends Omit<
  React.InputHTMLAttributes<HTMLInputElement>,
  'className' | 'style'
> {
  ref?: React.Ref<HTMLInputElement>;
}

export const Input: React.FC<IProps> = ({ ref, ...props }) => {
  return <input ref={ref} {...props} />;
};
```

- **NATIVE-9.** Добавляй `ref` только компоненту, который действительно пробрасывает конкретный нативный target.
- **NATIVE-10.** Сохраняй совместимость input-компонента с `react-hook-form`: передавай `ref`, `name`, `onChange` и `onBlur` нативному input. Не определяй этим скиллом механизм валидации.
- **NATIVE-11.** Не проектируй собственный polymorphic prop `as` в обычном компоненте. Полиморфный абстрактный компонент проектируй отдельно. Документированный `as` инфраструктурного root из `NATIVE-15` не является публичной полиморфностью создаваемого компонента.
- **NATIVE-12.** Используй нативный семантический элемент вместо имитации через `div`. Исключение требует обоснования и подтверждения.
- **NATIVE-13.** Не передавай готовому визуальному компоненту UI kit или сторонней библиотеки `className` и нативный CSS `style: React.CSSProperties` ради переопределения его внешнего вида. Размещай локальный класс на собственной семантической сущности или layout-слоте. Не путай CSS `style` с документированным семантическим union-prop библиотеки, например `<Button style="ghost" />`: такой prop является частью UI-контракта и допустим.
- **NATIVE-14.** Не вкладывай один интерактивный элемент в другой, например `Button` в `NavLink`. Сохраняй один корректный семантический интерактивный элемент.
- **NATIVE-15.** Если внешний инфраструктурный или animation primitive является фактическим DOM-узлом компонента либо его самостоятельной layout-границы, передавай ему локальный `className`, документированный `as` для выбора семантического элемента и runtime `style`, содержащий MotionValue, transform или результат измерения, который нельзя выразить статическим CSS-классом. Это root-интеграция, а не визуальная кастомизация готового UI-компонента. Статические layout и decoration values по-прежнему размещай в CSS Module.

## STATE — состояние

- **STATE-1.** Делай абстрактный переиспользуемый компонент controlled: `value`, `checked`, `open` приходят через props вместе со смысловым callback.
- **STATE-2.** Получай управляющее состояние локального сценарного компонента из готового controller/context/framework-механизма. Не создавай искусственные `value/onChange` или `open/onOpen` props между локальными компонентами.
- **STATE-3.** Uncontrolled-режим абстрактного компонента допускай только после остановки, обоснования и подтверждения разработчика.
- **STATE-4.** Разрешай локальный state для внутреннего технического UI-состояния, которое не является управляющим контрактом компонента.
- **STATE-5.** Не копируй props в state. Не храни две независимые копии одних данных.
- **STATE-6.** Не изменяй props и state напрямую. Создавай новое значение.
- **STATE-7.** Если новое состояние зависит от предыдущего, используй функциональную форму setter.
- **STATE-8.** Не храни производное значение в state. Вычисляй его из актуальных props/state и применяй memoization только по критериям `HOOK-6` и `HOOK-8`.
- **STATE-9.** Для тяжёлой инициализации используй lazy initializer `React.useState(() => createInitialValue())`.
- **STATE-10.** Если несколько частей state образуют единый процесс и меняются согласованно, используй `React.useReducer`.
- **STATE-11.** Выноси самостоятельный reducer в `reducer/<name>.reducer.ts`. Reducer является чистой функцией без I/O, hooks и мутации state.

## HOOK — hooks и memoization

- **HOOK-1.** Соблюдай Rules of Hooks: вызывай hooks только на верхнем уровне function component или custom hook.
- **HOOK-2.** Используй effect только для синхронизации с внешней системой, а не для вычисления производных значений.
- **HOOK-3.** Каждый effect с subscription, timer, observer или listener возвращает cleanup.
- **HOOK-4.** Асинхронная работа внутри компонента является исключением: её выполняют controller и framework. Не добавляй async-effect без обоснования и подтверждения.
- **HOOK-5.** Если исключительный async-effect подтверждён, используй async IIFE внутри обычного `React.useEffect`, а не `async` callback самого effect.
- **HOOK-6.** Выноси производное значение из JSX, когда это улучшает читаемость. Используй `React.useMemo` только для дорогого вычисления, требуемой потребителем или dependency стабильности ссылки либо значимого сохранения identity создаваемого объекта или коллекции. Простое scalar-вычисление, построение строки пути и обычный framework getter вычисляй без memoization.
- **HOOK-7.** Не добавляй return type callback внутри `useMemo`, если TypeScript точно выводит его.
- **HOOK-8.** Используй `React.useMemo`, `React.useCallback`, `React.memo` и HOC-мемоизацию только при фактической пользе, требовании стабильной ссылки или доказанной проблеме производительности.
- **HOOK-9.** Простые inline callbacks в JSX разрешены. Не выноси и не memoize их формально.
- **HOOK-10.** Размещай component-local hook в `hooks/<name>.hook.ts`, называй функцию `use...` и экспортируй именованно. Не экспортируй hook из фасада компонента.
- **HOOK-11.** Передавай независимые параметры hook позиционно. Используй объект только когда он является одной цельной моделью. Большое число аргументов требует остановки и декомпозиции.
- **HOOK-12.** Hook возвращает объект с именованными полями. Массив используй только для tuple-контракта.
- **HOOK-13.** Полагайся на точный вывод результата. Если объектный контракт нельзя качественно вывести и inline-тип загрязняет сигнатуру, объяви внутренний `interface IReturn` в hook-файле.
- **HOOK-14.** Используй `React.useRef` для DOM access, focus, measurements, scroll и внешнего imperative API, но не для хранения управляющего состояния.
- **HOOK-15.** `React.useImperativeHandle` запрещён по умолчанию и требует отдельного обоснования и подтверждения.

## REACTIVE — локальная реактивность

- **REACTIVE-1.** Предпочитай локальную reactive-границу вокруг конкретного чтения. Считай `<Reactive>` согласованным framework-исключением из запрета render props:

```tsx
<Reactive>{() => data.name}</Reactive>
```

- **REACTIVE-2.** Не оборачивай весь компонент в `reactive` без необходимости. Используй `reactive(Component)` только когда reactive-чтения распределены по всему компоненту и локальные `<Reactive>` усложняют JSX.
- **REACTIVE-3.** Для HOC допустим внутренний `<Name>Component` и публичный `<Name>`:

```tsx
const InputComponent: React.FC<IProps> = (props) => {
  return <input />;
};

export const Input = reactive(InputComponent);
```

- **REACTIVE-4.** Не дублируй явную типизацию результата HOC, если тип компонента сохраняется корректно.
- **REACTIVE-5.** Не используй сокращённую форму `reactive(() => ...)`. Всегда объявляй именованное тело `<Name>Component` и отдельно экспортируй результат HOC.

## COMP — композиция и JSX

- **COMP-1.** Создавай один собственный DOM-root с локальным классом `s.wrapper`, когда компонент имеет собственную визуальную, семантическую или layout-границу. Не добавляй бессмысленный wrapper вокруг единственного готового control: технический или управляющий компонент может вернуть его напрямую.
- **COMP-2.** Строй сложный компонент рекурсивным слоением. Композиционный родитель отвечает только за свой wrapper, layout-слоты и размещение непосредственных детей; каждый ребёнок может быть таким же композиционным узлом.
- **COMP-3.** Если появился самостоятельный логический слой `header`, `aside`, `content`, `footer`, `actions` или аналогичная роль, сразу оформляй его отдельным дочерним компонентом независимо от текущего количества элементов.
- **COMP-4.** Оставляй layout-слот в родителе: `<div className={s.header}><Header /></div>`. Не реализуй внутри слота содержимое слоя через `Typography`, `Button` или другие конкретные элементы.
- **COMP-5.** Завершай слоение на финальной логической композиции отображения или управления. Она может содержать несколько DOM- и UI-kit элементов, если они вместе реализуют одну цельную роль и дальнейшее разделение не создаёт самостоятельной ответственности.
- **COMP-6.** Не создавай дочерний компонент для формальной обёртки текста, одного DOM-узла или другой части без собственного контракта, поведения, управления либо логической роли.
- **COMP-7.** Пересматривай финальность при росте компонента: когда внутренняя часть получает собственное отображение, состояние или управление, выделяй её в ребёнка, а текущий компонент превращай в композиционного родителя.
- **COMP-8.** Разрешай локальному финальному управляющему компоненту получить готовый controller и связать UI-событие с его командой. Не проектируй этим скиллом controller и application flow.
- **COMP-9.** Используй fragment `<>...</>` только когда дополнительный DOM-wrapper технически нарушает HTML-структуру, например между `tr` и несколькими `td`. Не добавляй fragment вокруг одного элемента.
- **COMP-10.** Родитель управляет отображением ребёнка. Обычный компонент не скрывает себя через `return null`.
- **COMP-11.** Не дублируй одинаковое JSX-дерево ради отличающегося значения. Для boolean-выбора между разными отображениями используй ternary; для нескольких смысловых или расширяемых состояний — фабричный компонент.
- **COMP-12.** Оформляй JSX-фабрику обычным дочерним компонентом с обязательным суффиксом `Factory`. Фабрика владеет каталогами всех выбираемых компонентов, содержит явный `switch`, не создаёт каталог `factory/` и может вернуть выбранного ребёнка без DOM-root.
- **COMP-13.** Отличай JSX-фабрику от чистой фабрики данных: чистую функцию без JSX размещай в `factory/<name>.factory.ts`.
- **COMP-14.** Допускай `null` из фабрики только как крайнюю защиту; нормальный родитель не вызывает её без варианта.
- **COMP-15.** Используй `&&` только с boolean-условием.
- **COMP-16.** Не проектируй собственные render props и именованные JSX slots без обоснования и подтверждения. Потребляй готовый библиотечный render-prop API без согласования и не добавляй лишний Fragment.
- **COMP-17.** `React.cloneElement` и скрытое изменение props ребёнка запрещены по умолчанию. Compound-модель проектируй отдельно.
- **COMP-18.** Не описывай создание Context и Provider этим скиллом.
- **COMP-19.** Не используй index массива как `key`. Если стабильной идентичности нет, остановись, обоснуй исключение и запроси подтверждение.
- **COMP-20.** `dangerouslySetInnerHTML` запрещён по умолчанию и требует обсуждения источника и очистки HTML.
- **COMP-21.** `event.preventDefault()` и `event.stopPropagation()` допустимы только когда компонент осознанно заменяет конкретное нативное поведение, а не скрывает неверную структуру.
- **COMP-22.** Определяй границу по ответственности, а не по числу JSX-элементов. Выделяй часть, когда у неё есть именуемая самостоятельная роль, собственные данные, действие, состояние или контракт либо когда родитель иначе смешивает несколько ролей. Оставляй финальной композицию, элементы которой совместно выполняют одну неделимую задачу.
- **COMP-23.** Считай compound-слоты готовой библиотеки вроде `Field.Label`, `Field.Content` и `Field.Caption` внутренней анатомией одного control: их наличие само по себе не требует отдельных локальных компонентов. Цельное поле с label, control, mapping и ошибкой может быть финальным field-компонентом внутри большей композиции.

## FUNC — внутренние функциональные роли

- **FUNC-1.** Оставляй обычную локальную чистую функцию в `*.tsx`, если она используется только компонентом.
- **FUNC-2.** Выноси самостоятельные mapper, serializer, factory и reducer в каталоги соответствующих ролей.
- **FUNC-3.** В component/view слое реализуй mapper, serializer и factory именованными arrow functions, а не классами.
- **FUNC-4.** Mapper, serializer, factory и reducer являются чистыми функциями: без I/O, hooks, мутации аргументов и скрытого внешнего состояния.
- **FUNC-5.** Не экспортируй внутренние функциональные роли из публичного фасада компонента.

## CSS — CSS Modules

- **CSS-1.** Импортируй stylesheet как `s`: `import s from './default.module.scss'`.
- **CSS-2.** При композиции классов импортируй `cn` через `import cn from 'classnames'`.
- **CSS-3.** Для одного класса используй `className={s.wrapper}`. Любую композицию через `cn` вынеси в `<element>ClassName`; memoize её только по критериям `HOOK-6` и `HOOK-8`.
- **CSS-4.** Передавай в `cn` базовые классы первыми, затем объект условных классов:

```tsx
const wrapperClassName = cn(s.wrapper, s['size--medium'], {
  [s.active]: props.active,
});
```

- **CSS-5.** Называй обычные классы по сущности в `kebab-case`: `wrapper`, `lead-icon`, `content`, `focused`.
- **CSS-6.** Для любой группы вариантов разрешай SCSS-модификаторы через `&--`:

```scss
.size {
  &--medium {
  }
  &--small {
  }
}
```

- **CSS-7.** Не используй BEM-дерево элементов вроде `button__icon__label`. Самостоятельная часть становится дочерним компонентом.
- **CSS-8.** Запрещены голые tag selectors, universal selectors и структурные костыли: `.wrapper button`, `.wrapper svg`, `.wrapper > *`, `.wrapper *`.
- **CSS-9.** Разрешай вложенность только по явным локальным классам, состояниям, pseudo selectors и media/container queries.
- **CSS-10.** `!important` и `:global(...)` запрещены по умолчанию и требуют обоснования и подтверждения.
- **CSS-11.** Статические inline styles запрещены. Runtime style инфраструктурного root допускай только по `NATIVE-15`; документированный семантический prop UI kit с именем `style` не является inline CSS.
- **CSS-12.** Используй существующие design tokens. Если подходящего токена нет, остановись и запроси подтверждение до hardcoded-значения.
- **CSS-13.** Разрешай соседний селектор `& + &`. Если обычный родительский контейнер естественно выражает то же расстояние через `gap`, добавляй `low`-рекомендацию перейти на `gap`, но не считай `& + &` обязательным рефакторингом.
- **CSS-14.** Каждое обращение `s.<name>` или `s['<name>']` должно разрешаться в объявленный локальный CSS Module class. Считай отсутствующий класс `medium`, а при поломке поведения или публичного контракта повышай приоритет по последствию. Неиспользуемые объявления проверяй по `STR-12`.

## API — публичная граница

- **API-1.** Публичный `index.ts` явно экспортирует только основной компонент.
- **API-2.** Не экспортируй `IProps`, children, hooks, mapper, serializer, factory, reducer, styles и внутренних детей.
- **API-3.** При декорировании другого компонента получай его контракт через `React.ComponentProps<typeof Component>`, не экспортируя его приватный `IProps`.
- **API-4.** Не создавай параллельный legacy export. Обновляй непосредственных потребителей в одном изменении.
- **API-5.** Не импортируй локального ребёнка, hook, factory, mapper, reducer, serializer или stylesheet за пределами компонента-владельца. Наружу доступен только основной компонент через его `index.ts`.
- **API-6.** Делай вынесенный в `library/design` компонент абстрактным: он не знает о controller, Context и data source конкретной страницы и получает данные и управление через публичный props-контракт.

- **FORMAT-1.** Проверяй Prettier для целевых файлов. Агрегируй все найденные отличия в одно `low`-нарушение с количеством ошибок и файлов.
- **LINT-1.** Запускай lint затронутого пакета и назначай важность каждой целевой группе ошибок по нарушенному правилу.
- **TYPE-1.** Запускай TypeScript-проверку. Считай ошибку в целевом компоненте `high`.
- **CHECK-1.** Если проверка падает из-за инструмента, конфигурации или только внешних файлов, отмечай её заблокированной, а не создавай нарушение целевого компонента.

Проверь компонент по всем применимым группам правил:

1. Объявление, каталог, имя, фасад и дочернее дерево.
2. Props, controlled-контракт, native attributes, refs и callbacks.
3. State, hooks, memoization, reactive-границы и JSX.
4. Внутренние функциональные роли и направление импортов.
5. CSS Modules, tokens, отсутствие запрещённых selectors и двустороннее соответствие каждого `s.<name>` объявленному локальному классу.
6. Владение данными и управлением, отсутствие prop drilling, направление импортов и число владельцев локальных детей.
7. Отсутствие мёртвого кода, tests/stories и соответствие затронутых `AGENTS.md`.
8. Результаты Prettier, lint и TypeScript для целевой границы.

Назначай приоритет:

- `critical` — runtime loop, нарушение Hooks, повреждение или потеря пользовательского состояния, внешний импорт приватной реализации компонента;
- `high` — сломанный native/public contract, вложенные интерактивные элементы, неверный ref, stale reactive UI, опасный escape hatch, самостоятельный слой внутри композиционного родителя, prop drilling, локальные data/управляющие props вне прямого контракта элемента коллекции из `PROP-20` или TypeScript-ошибка в целевом компоненте;
- `medium` — избыточная декомпозиция, мёртвый код, неверная роль, props, memoization, фасад, CSS-граница и любое формальное нарушение обязательного стандарта;
- `low` — рекомендация без обязательного рефакторинга, включая предпочтение `gap` допустимому `& + &`, и ошибки Prettier;
- для lint используй важность нарушенного правила от `low` до `high`.

Перед списком выведи количество нарушений по приоритетам и правилам. Каждое нарушение выводи отдельной строкой:

```text
<PRIORITY> | <RULE-ID> | <target-or-file:line> | <фактическое нарушение> | <точное исправление>
```

Не объединяй разные позиции архитектурных нарушений. Инструментальные ошибки агрегируй по одной проверке, указывая количество ошибок и файлов, потому что они устраняются одним действием. Если инструмент падает из-за конфигурации или сообщает ошибки только за пределами цели, не приписывай их компоненту: отметь проверку заблокированной и перечисли внешние файлы и сообщения. Не объявляй компонент полностью проверенным при заблокированной проверке. Если нарушений нет, перечисли проверенные группы правил.
