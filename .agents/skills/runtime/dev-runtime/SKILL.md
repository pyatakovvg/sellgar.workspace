# Локальный runtime

## Режим и контекст

Определи цель: запустить приложение, диагностировать сбой или подтвердить конкретный сценарий. Команды, ports, dependency graph, environment contracts и способ readiness получай из локальных инструкций, manifests и конфигурации. Не требуй HTTP health от компонента, чей контракт его не предусматривает.

Для запуска всего приложения следуй его документированному профилю. Для одного endpoint выбери минимальный набор зависимостей; название UI не разрешает запуск всех соседних приложений.

## Процессы и ресурсы

1. Проверь действующие процессы, listening ports и containers в scope, установи их cwd и назначение. Не выводи широкие command lines, если они могут содержать credentials.
2. Переиспользуй соответствующие checkout корректные процессы. Запусти отсутствующие зависимости в порядке их фактических связей, в отдельных наблюдаемых sessions.
3. Получи readiness каждого нового процесса: compile/startup success, соединение с broker/storage, listening endpoint или иное обещание компонента.
4. Выполни запрошенный smoke/API/browser сценарий. Если запрос был только на старт, не запускай полный acceptance suite без необходимости; readiness всё равно обязателен.
5. Оставь процессы, нужные пользователю для работы, активными. Временные диагностические процессы останови.

Не останавливай владельца занятого порта до диагностики. Запуск сам по себе не разрешает sync source, upgrade dependencies, изменение env contracts, удаление cache/storage или пересоздание volumes. При внешнем ограничении используй допустимый способ выполнения того же действия, сохраняя scope.

## Контракты и evidence

Для auth/session подключай [auth-session](../../contracts/auth-session/SKILL.md), для межсервисного поведения — [service-contracts](../../contracts/service-contracts/SKILL.md). Build подтверждает компиляцию, а не сохранение данных, cookies, события или отображение UI.

Фиксируй exact method/URL, status, смысл ответа и релевантные browser steps. Не сохраняй secret values. Различай транспортный отказ, отсутствие объекта, отказ доступа и ошибку upstream.

Диагностика без запроса на исправление завершается evidence/verdict. При разрешённом исправлении переходи к [development-workflow](../../workflows/development-workflow/SKILL.md), а затем повтори затронутый сценарий. Не пытайся исправлять environment failure изменением production behavior.

В конце сообщи запущенные/переиспользованные sessions, readiness, выполненный сценарий и ограничения. Проверь tracked state, чтобы незапрошенные generated/config changes не попали в результат.
